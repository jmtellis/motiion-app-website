## Eighth defensive migration: captured submission origin

The completed defensive migration has three related parts:

1. Add nullable `submissions.submitted_by`. A database INSERT trigger always assigns `auth.uid()`, including calls inside SECURITY DEFINER RPCs; supplied values are ignored. Authenticated talent submissions therefore record the talent. Operator-created selections record the operator. Service/database inserts without an authenticated actor remain NULL. Existing rows remain NULL; no fabricated backfill.
2. Make `id`, `role_id`, `talent_id` and `submitted_by` immutable to ordinary requests. The exception examines the request's signed role before the execution role, so a normal authenticated caller cannot bypass it merely by entering a SECURITY DEFINER function. Only service-role requests or trusted direct database maintenance without request identity can repair these fields. Normal status, notes, review dates, answers and media retain their existing RLS behavior.
3. Require `submitted_by = talent_id` for the private-profile submission exception. Keep public/self/service card paths intact. Prevent the existing account-snapshot trigger from automatically copying another person's email/resume/private media into an operator-created submission. Genuine authenticated applicant snapshots remain unchanged. Explicit operator-supplied material is retained, and active public profile name/headshot fallback remains available.

The migration explicitly attaches `require_casting_applicant_account` using the exact production trigger name, replacing its function narrowly to retain all account/age/profile eligibility checks. The new provenance trigger is separate. Initial staging verification found that this older branch lacked the native snapshot trigger already present in production. The explicit attachment correction was reviewed and approved before application; the positive suite then passed. Snapshot authorization uses the current request identity directly, so it does not depend on trigger-name ordering.
